# 批量匹配第四轮：紧凑查询特征与分词分配优化

2026-11-04，接续[第三轮](batch-matching-round3-performance.zh-CN.md)，继续优化共享 Rust/WASM 搜索核心。实现位于 [search.rs](../wasm/converter-core-rust/src/text/search.rs)，未新增运行时依赖。

后续：[第五轮：按需提取文件名词频](batch-matching-round5-performance.zh-CN.md)，继续降低文件名搜索的分配与中文深层路径的内存占用。

## 实现与语义

结果块的查询特征从字符串 BTreeMap 改为有序的 `(查询词编号, 词频)` 列表，仅存命中的查询词。编号沿用查询词的原有字典顺序；评分时顺序读取数值列表，保留未命中词的零贡献、浮点求和顺序、数字词必须命中等规则。第一遍仍使用完整词频表的原有顺序计算文档长度，之后释放临时表；缓存中不再保留每个结果块的查询词字符串和树节点。

特征缓存预算保持 8 MiB。计费从旧树条目的 `词长 + 80` 估算，改为数值列表的实际 `capacity × size_of((usize, f64))`；列表结构、其他索引和临时分词表不计入该缓冲区预算。这会改变可缓存的块数，预算耗尽时仍重新提取该块的查询特征，评分结果保持一致。它不是整个搜索操作的内存上限。

分词更新词频时，已存在的词直接借用字符串查找并累加；新词才复制字符串。中文单字使用 UTF-8 栈缓冲区，双字词复用一个字符串缓冲区，减少重复字符与词组的临时分配。停用词、重复词权重、连字符拆分、数字编号、Unicode 规范化与来源位置保持原有行为。

## 性能

Apple M4 Pro、Node.js v20.20.2，通过现有前端 `InMemoryWasiHost` 运行生产文本 WASM。计时包含新实例创建、内存文件读取、JSON 解析、检索评分、序列化和结果写入；编译、host 初始化、输入生成、读取结果、断言和哈希在计时外。前后交替运行，预热 3 轮、测量 9 轮，取中位数。

| 用例 | 修改前 | 修改后 | 加速 |
| --- | ---: | ---: | ---: |
| 英文 BM25，32 文件 | 1.402 ms | 1.077 ms | 1.30 倍 |
| 英文 BM25，1,000 文件 | 14.96 ms | 13.75 ms | 1.09 倍 |
| 64 个长文件，深层目录，文件名短语命中 | 137.22 ms | 129.88 ms | 1.06 倍 |
| 同上，文件名短语不命中 | 136.53 ms | 127.94 ms | 1.07 倍 |
| 中文 BM25，64 文件 | 174.94 ms | 133.01 ms | **1.32 倍** |
| 16 查询词、64 文件 | 96.16 ms | 86.11 ms | 1.12 倍 |
| 文件名分词搜索，1 万文件 | 34.57 ms | 33.98 ms | 基本持平 |
| 字面精确搜索，1 万文件，对照 | 16.42 ms | 16.43 ms | 基本持平 |
| 16 查询词、6,400 块，旧缓存超限 | 244.54 ms | 214.17 ms | 1.14 倍 |
| 64 查询词、10,240 块，新旧缓存均超限 | 702.01 ms | 495.57 ms | **1.42 倍** |
| 128 查询词、仅两词命中，64 文件 | 31.06 ms | 27.51 ms | 1.13 倍 |

稀疏用例的命中词位于查询序列中间，前后及两词之间都有缺失项，验证编号没有在压缩列表时被错误移动。64 词用例的结果还验证了新缓存超限后的回退路径。所有计时轮次均检查完整响应哈希。

这是完整 WASM 搜索操作的组合收益，不是查询列表读取的单独微基准；不包含文件提取、目录扫描、磁盘读写、浏览器界面、OCR 推理和 CLI 启动。原生 CLI 引用同一份检索源码，本轮未单独测量原生 CLI 的耗时。

## 内存与取舍

以下数值为每次在新实例中执行完整操作后，`memory.buffer.byteLength` 的长度。该 WASM 线性内存只增长、不缩小，因此可反映其增长高水位；单位 MiB。它不是存活堆对象大小、物理驻留内存或整个进程的 RSS。

| 用例 | 修改前 | 修改后 | 变化 |
| --- | ---: | ---: | ---: |
| 文件名分词搜索，1 万文件 | 16.438 MiB | 14.188 MiB | −2.250 MiB |
| 16 查询词、6,400 块 | 16.500 MiB | 12.063 MiB | **−4.438 MiB，约 −27%** |
| 64 查询词、10,240 块 | 19.938 MiB | 23.375 MiB | **+3.438 MiB，约 +17%** |

64 词重负载会在相同预算内缓存更多块，减少回退时的重新分词，但实际使用的线性内存也更多。该用例以约 3.4 MiB 的额外内存换取 1.42 倍速度；本轮保留这一取舍。新缓存的数据缓冲区受 8 MiB 预算限制，不能据此宣称所有输入的总内存都下降。

## 体积与构建对照

| 生产 converter-text.wasm | 修改前 | 修改后 | 变化 |
| --- | ---: | ---: | ---: |
| 原始字节 | 8,513,892 | 8,510,704 | −3,188 |
| gzip，级别 9 | 3,182,520 | 3,181,096 | **−1,424** |
| Brotli，质量 11 | 2,292,987 | 2,293,603 | +616 |

三个指标独立压缩统计，Brotli 本轮增加 616 字节；没有把 gzip 的减少推广为所有传输或安装包体积均下降。未修改运行时 JavaScript。

前后均使用 Rust 1.93.0、`text-extraction,postscript`、`wasm32-wasip1` release、现有 `privateRustBuildEnv`，Binaryen 131.0.0 参数为 `-Oz --strip-debug --strip-producers --enable-bulk-memory --enable-nontrapping-float-to-int`。核对非空、WASM 有效性和 SHA-256。

最初公共构建目录返回了与源码不对应的缓存旧产物，已弃用；另一次构建因磁盘空间不足失败，也未计入数据。最终从独立源码副本重建基线，清除文本目标的构建指纹以强制编译；基线与第三轮优化后产物逐字节一致。优化版同样强制编译，避免将旧输出当作新产物。测量记录的 `baselineControl` 和产物哈希保存了这项核对。

```sh
node --no-warnings scripts/benchmark-batch-matching-round4.mjs \
  --baseline tmp/batch-matching-round4/before.wasm \
  --wasm tmp/batch-matching-round4/after.wasm \
  --control-baseline tmp/batch-matching-round3/after.wasm \
  --source-baseline benchmarks/frontend/2026-11-04/batch-matching-round4-source-baseline.json.gz \
  --output tmp/batch-matching-round4/replay.json
```

`--control-baseline` 可省略，提供时核对基线 SHA-256。添加 `--checks-only` 可只验证完整响应和采集线性内存，跳过计时与压缩计算。共享源码测试沿用[第三轮轻量入口及命令](batch-matching-round3-performance.zh-CN.md#记录与复跑)。
