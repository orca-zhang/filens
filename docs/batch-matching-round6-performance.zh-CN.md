# 批量匹配第六轮：先选择文件，再排序摘录

2026-11-04，接续[第五轮](batch-matching-round5-performance.zh-CN.md)，优化共享 Rust/WASM 搜索核心的结果选择。实现位于 [search.rs](../wasm/converter-core-rust/src/text/search.rs)，未新增运行时依赖。

后续：[第七轮：分词时直接提取查询特征](batch-matching-round7-performance.zh-CN.md)，省去正文完整词频表，继续优化正文 BM25 热路径。

## 实现与语义

原实现先给所有命中块完整排序，再统计命中文件，最后返回 `limit` 指定的最多 100 个文件。命中文件很多、只需要前几项时，大量比较不会影响最终结果；长公共路径前缀还会增加字符串比较成本。

新实现利用评分阶段保持文件顺序的特点，顺序扫描命中块，记录每个文件的最佳块，同时统计全部命中文件。当命中文件数超过返回上限时，用部分选择保留最佳文件，再仅对这些文件的命中块做原有稳定排序。文件计数不再构建 HashSet；扫描只需保存每个命中文件的一个索引。

文件排名沿用原来的分数降序、路径字典序、起始字节顺序；三项完全相同时，用命中块的原始序号保留稳定排序的输入顺序。部分选择虽然使用不稳定分区，最终文件边界仍采用这一完整比较规则，重复路径不会错误交换来源。

候选文件保留全部命中块，再按原规则贪心选择最多三段互不重叠的摘录。没有把全局前几个块直接当成返回结果，也没有在分词或评分前丢弃文件；BM25 的文档频率、评分和全部命中文件计数保持原值。未命中文件、总文件数、65,536 块上限及截断标记沿用原有行为。

这个改动减少完整排序与后续选择需要处理的块数，仍会先保存所有正分命中块；它不是流式检索或整次操作的内存上限。8 MiB 查询特征预算没有改动。

## 测量方法

Apple M4 Pro、Node.js v20.20.2，通过现有前端 `InMemoryWasiHost` 运行生产 `converter-text.wasm`。每次操作创建新实例，计时包含实例创建、内存文件读取、JSON 解析、检索评分、序列化和结果写入；编译、host 初始化、输入生成、输出读取、断言和哈希在计时外。预热 3 轮，测量 9 轮，前后版本交替执行，取中位数。每个计时轮次均核对完整响应哈希。

线性内存记录完整操作后 `memory.buffer.byteLength`，单位 MiB。WASM 内存只增长、不缩小，该指标反映其增长高水位，不代表存活堆对象、物理驻留内存或 Node 进程 RSS。不包含浏览器界面、目录扫描、文件提取、磁盘读写、OCR 推理或 CLI 启动耗时。

新增的大规模用例有 50,000 个文件，每个文件正文为空，名称包含字面查询词；目录有重复的中文公共前缀，文件顺序采用固定置换，避免输入恰好已排序。完整输入为 43,800,070 字节，包含路径与来源字段；匹配全部 50,000 个文件，仅输出前 10 个。1.39 倍是该完整操作的结果，不是单独排序的微基准，也不代表所有检索模式都有同样收益。

多数普通场景的变化较小；本轮仍有回退：空正文 BM25 从 20.32 ms 增至 21.25 ms，约 +4.6%，中文 BM25 约 +1.3%。表中保留这些结果。

## 验证

- 16 项共享搜索源码测试通过。新增测试覆盖 1、2、100 个返回文件的边界、全部命中文件计数、重复路径下的偏移与输入顺序，以及保留三段贪心选择的非重叠摘录。
- 51 组本轮生产 WASM 完整响应对照通过。在第五轮 36 组基础上，新增三种搜索模式与 1、2、10、100 四档上限的组合、5 万文件乱序中文深层路径、重复路径稳定性和摘录保留用例。组合用例包含重复路径、不同分数、起始位置、来源哈希、部分来源标记及归档信息。
- 24 组精确搜索与 Office 媒体操作、5 组 OCR 响应对照再次通过，合计 **80 组完整响应对照**。仅忽略 `metrics.elapsedMs`，评分等字段严格比较；OCR 推理使用固定 host 响应，实际执行生产解析、过滤与来源映射。
- 转换架构边界检查 2,122 项通过。
