# 批量匹配第七轮：分词时直接提取查询特征

2026-11-04，接续[第六轮](batch-matching-round6-performance.zh-CN.md)，优化共享 Rust/WASM 核心的正文分词与查询特征提取。实现位于 [search.rs](../wasm/converter-core-rust/src/text/search.rs)，未新增运行时依赖。

后续测量见[第八轮：借用分词切片并复用正文规范化](batch-matching-round8-performance.zh-CN.md)。

## 实现与语义

原实现为每个正文块建立完整词频 BTreeMap，合并文件名词频，计算块长度，再从中提取查询词频。其余正文词的字符串与树节点在这一轮之后就会释放，但构建它们的开销已经发生。

新实现把分词规则抽成共享的词与权重遍历。查询与文件名仍用它建立原有完整词频表；正文遍历则直接累计块长度，并通过一次编译的查询词索引更新查询频率。无关正文词只贡献长度，不再为它们分配字典键与树节点。每块复用同一份数值暂存数组，清零后重新累计，最后按原有查询词编号输出稀疏特征列表。

所有词仍计入块长度。现有分词权重均为 0.25 的整数倍，在输入上限内可以用 f64 精确累计，因此从按词频表求和改为按发射权重求和不改变块长度。查询词的正文频率按原有遍历顺序更新，再加上文件名的封顶频率。NFKC、大小写转换、停用词、连字符与数字编号、中文单字和双字词、扩展区汉字沿用同一套分词规则。

文件名仍先完整分词并按词封顶为 2，缓存当前文件。文件名模式直接在这张表中查找查询词并按原顺序求长度，避免遍历全部名称词时重复匹配查询。精确模式不调用这条分词路径。

查询特征预算保持 8 MiB，计费方式仍为稀疏数值列表的实际容量。超预算时重新提取特征；查询编号、文档频率、BM25 浮点评分顺序、短语加分、排名、摘录和来源映射没有改动。仍会分配规范化字符串、分词缓冲区、特征列表等结构，本轮没有消除每块的所有分配，也没有为整个检索设置内存上限。

## 测量方法

Apple M4 Pro、Node.js v20.20.2，通过前端真实的 `InMemoryWasiHost` 执行生产 `converter-text.wasm`，每次操作创建新实例。计时包含实例创建、内存文件读取、JSON 解析、检索评分、序列化与结果写入；编译、host 初始化、输入生成、输出读取、断言和哈希在计时外。前后交替执行，预热 3 轮、测量 9 轮，取中位数，每次计时操作均验证完整响应哈希。

线性内存取完整操作后的 `memory.buffer.byteLength`，单位 MiB。WASM 内存只增长、不缩小，此指标反映其增长高水位，不代表存活堆对象、物理驻留内存或 Node 进程 RSS。不包含浏览器界面、目录扫描、文件提取、磁盘读写、OCR 推理或 CLI 启动耗时。

## 性能

| 用例 | 修改前 | 修改后 | 加速 |
| --- | ---: | ---: | ---: |
| 英文 BM25，32 文件 | 0.990 ms | 0.970 ms | 1.02 倍 |
| 英文 BM25，1,000 文件 | 13.69 ms | 13.33 ms | 1.03 倍 |
| 64 个长文件，深层目录，文件名短语命中 | 123.91 ms | 105.19 ms | **1.18 倍** |
| 同上，文件名短语不命中 | 126.49 ms | 106.57 ms | **1.19 倍** |
| 中文 BM25，64 文件 | 130.72 ms | 113.80 ms | **1.15 倍** |
| 16 查询词、64 文件 | 84.23 ms | 81.78 ms | 1.03 倍 |
| 文件名搜索，1 万英文名称 | 30.78 ms | 30.76 ms | 基本持平 |
| 文件名搜索，1 万中文深层路径 | 425.94 ms | 433.86 ms | 0.98 倍 |
| BM25，1 万中文深层路径，正文均为空 | 21.79 ms | 21.38 ms | 1.02 倍 |
| 字面精确搜索，1 万文件 | 16.32 ms | 16.08 ms | 1.01 倍 |
| 16 查询词、6,400 块 | 215.28 ms | 207.45 ms | 1.04 倍 |
| 64 查询词、10,240 块，特征缓存超限 | 493.77 ms | 365.66 ms | **1.35 倍，耗时 −26%** |
| 128 查询词、仅两词命中，64 文件 | 27.03 ms | 26.44 ms | 1.02 倍 |
| 字面精确搜索，5 万乱序中文深层路径 | 333.11 ms | 336.42 ms | 0.99 倍 |
| 128 种正文词、32 文件，查询仅一个词 | 247.68 ms | 161.55 ms | **1.53 倍，耗时 −35%** |
| 256 查询词、仅两词命中，64 文件 | 32.11 ms | 28.19 ms | **1.14 倍** |

正文词汇用例在每份文件中重复包含 128 种不同词的段落，并加入查询词；总计 6,944 个块，各块依旧受 640 字符上限约束，并非每块都有全部 128 词。新实现无需保存这些无关正文词，完整操作加速 1.53 倍。

稀疏查询的命中词位于查询编号中间，验证未命中的编号没有在压缩列表时被错误移动；64 词压力用例同时验证特征预算耗尽后的重新提取路径。各用例都是完整 WASM 操作，不能把 1.53 倍推广为所有正文、所有查询的收益。

文件名搜索和精确搜索变化较小，仍有回退：中文深层路径文件名搜索约 +1.9%，5 万文件精确搜索约 +1.0%。本轮保留这些测量结果。

## 验证

- 18 项共享搜索源码测试通过。新增完整词频表参考对照，逐项验证块长度、查询编号与词频，并反复切换文件验证暂存数组清零；另有无关正文词仍影响长度归一化排名的回归。已有 0、128 字节与默认特征预算的一致性测试继续通过。
- 55 组本轮生产 WASM 完整响应对照通过。在第六轮 51 组基础上，新增含 128 种正文词的重复语料、256 词稀疏查询、无关词对长度与排名的影响，以及混合 Unicode、数字、复合词与名称封顶用例。
- 24 组精确搜索与 Office 媒体操作、5 组 OCR 响应对照再次通过，合计 **84 组完整响应对照**。仅忽略 `metrics.elapsedMs`，评分使用严格数值比较；OCR 推理使用固定 host 响应，实际执行生产解析、过滤与来源映射。
- 转换架构边界检查 2,122 项通过。
